# AI 伦理治理与合规

> AI 的能力越强，其潜在危害越大。从招聘歧视到自动驾驶事故，从深度伪造到隐私泄露，每一项 AI 失效事件都在拷问开发者：我们构建的究竟是工具还是责任？AI 伦理治理不再是"锦上添花"的公关话题，而是法律强制、商业必需、技术约束三重维度的硬性要求。本文系统梳理 AI 伦理的核心议题、技术对策、法规框架与企业实践。

---

## 一、AI 伦理的核心议题

### 1.1 七大核心议题

| 议题 | 核心问题 | 典型案例 |
|------|---------|---------|
| **公平性** | 模型是否对某些群体系统性不利 | 亚马逊招聘 AI 偏向男性 |
| **隐私** | 训练/推理是否侵犯个人隐私 | Clearview AI 抓取社交照片 |
| **可解释性** | 决策是否可被理解与申诉 | 信用评分被拒原因不明 |
| **透明性** | 用户是否知道在与 AI 交互 | ChatGPT 装人类事件 |
| **问责制** | 出错时谁负责 | 自动驾驶事故责任划分 |
| **安全鲁棒** | 是否可被对抗攻击误导 | 对抗样本欺骗视觉模型 |
| **社会影响** | 对就业、民主、文化的长期影响 | Deepfake 干扰选举 |

### 1.2 伦理与技术的关系

伦理不是"做完了再加"的装饰，而是**贯穿设计-数据-训练-部署-监控**全流程的约束。负责任 AI（Responsible AI, RAI）的核心理念：在能力（Capability）与可控性（Control）之间寻找平衡。

## 二、公平性与偏见评估

### 2.1 偏见的来源

```
历史数据偏见 -> 标注偏见 -> 特征选择偏见 -> 模型放大偏见 -> 部署反馈偏见
```

偏见的来源可能在数据生命周期任意环节注入，并逐级放大。

### 2.2 公平性定义（互不兼容的多重定义）

| 定义 | 数学表述 | 含义 |
|------|---------|------|
| **统计均等** (Demographic Parity) | P(Ŷ\|A=0) = P(Ŷ\|A=1) | 各群体被预测为正的比例相等 |
| **机会均等** (Equal Opportunity) | P(Ŷ=1\|Y=1, A=0) = P(Ŷ=1\|Y=1, A=1) | 在真正例上各群体相等 |
| **预测均等** (Predictive Parity) | P(Y=1\|Ŷ=1, A=0) = P(Y=1\|Ŷ=1, A=1) | 预测为正的精度各群体相等 |
| **校准** (Calibration) | P(Y=1\|S=s, A=0) = P(Y=1\|S=s, A=1) | 评分对各群体含义一致 |

> 注意：在基础率不同的情况下，上述多个定义**不可能同时满足**（Impossibility Theorem, Kleinberg et al. 2016）。设计时必须明确选择哪个公平性目标。

### 2.3 偏见评估示例

```python
from fairlearn.metrics import demographic_parity_difference, equalized_odds_difference
from sklearn.metrics import accuracy_score

y_pred = model.predict(X_test)
sensitive = X_test['gender']   # 敏感属性

print("整体准确率:", accuracy_score(y_test, y_pred))
print("统计均等差异:", demographic_parity_difference(y_test, y_pred, sensitive_features=sensitive))
print("机会均等差异:", equalized_odds_difference(y_test, y_pred, sensitive_features=sensitive))
# 差异 < 0.1 通常视为可接受
```

### 2.4 缓解策略

| 阶段 | 方法 | 例子 |
|------|------|------|
| 预处理 | 改造数据分布 | 重采样、公平表示学习 |
| 训练中 | 加入公平性约束 | 对抗去偏、正则项 |
| 后处理 | 调整预测结果 | 不同群体不同阈值 |

## 三、隐私保护（差分隐私、联邦学习）

### 3.1 差分隐私（Differential Privacy, DP）

**核心思想**：让模型无法判断某个个体是否在训练集中，从而保护个体隐私。

形式化定义：对于任意两个仅差一条记录的数据集 D 和 D'，算法 M 满足：

```
P(M(D) ∈ S) ≤ e^ε · P(M(D') ∈ S) + δ
```

- ε（隐私预算）：越小越隐私，但效用越低
- δ：失败概率，通常取 1/n

```python
# 使用 Opacus 实现 DP 训练
from opacus import PrivacyEngine
from torch.optim import SGD

optimizer = SGD(model.parameters(), lr=0.01)
privacy_engine = PrivacyEngine()

model, optimizer, dataloader = privacy_engine.make_private(
    module=model,
    optimizer=optimizer,
    data_loader=dataloader,
    noise_multiplier=1.0,    # 噪声大小
    max_grad_norm=1.0,       # 梯度裁剪
)
# 训练后可查询已消耗的隐私预算
print(privacy_engine.get_epsilon(delta=1e-5))
```

### 3.2 联邦学习（Federated Learning）

**核心思想**：数据不动模型动，原始数据不出本地。

```
                ┌─────────────┐
                │  中心服务器   │
                │  聚合梯度     │
                └──────┬──────┘
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
   ┌─────────┐    ┌─────────┐    ┌─────────┐
   │ 设备 A   │    │ 设备 B   │    │ 设备 C   │
   │ 本地训练 │    │ 本地训练 │    │ 本地训练 │
   │ 原始数据 │    │ 原始数据 │    │ 原始数据 │
   └─────────┘    └─────────┘    └─────────┘
```

| 项目 | 横向联邦 | 纵向联邦 |
|------|---------|---------|
| 数据划分 | 样本不同，特征相同 | 样本相同，特征不同 |
| 典型场景 | 多手机端 | 多机构合作（如银行+电商） |
| 代表框架 | FedAvg | FATE、SecretFlow |

### 3.3 隐私增强技术（PET）对比

| 技术 | 保护对象 | 优势 | 劣势 |
|------|---------|------|------|
| 差分隐私 | 个体记录 | 数学严格保证 | 引入噪声，精度下降 |
| 联邦学习 | 原始数据 | 数据不出域 | 通信开销大 |
| 同态加密 | 计算过程 | 可加密计算 | 极慢（10-1000x） |
| 安全多方计算 | 多方联合计算 | 无信任假设 | 通信复杂 |
| 可信执行环境 | 运行时 | 性能好 | 信任硬件厂商 |

## 四、可解释性要求与法规

### 4.1 可解释性层级

| 层级 | 含义 | 方法 |
|------|------|------|
| 全局解释 | 模型整体如何决策 | 特征重要性、规则抽取 |
| 局部解释 | 单次预测为何如此 | SHAP、LIME、Counterfactual |
| 过程解释 | 推理步骤可见 | Chain-of-Thought、归因可视化 |

### 4.2 SHAP 示例

```python
import shap
explainer = shap.TreeExplainer(model)
shap_values = explainer.shap_values(X_test)

# 单样本解释
shap.force_plot(explainer.expected_value, shap_values[0], X_test.iloc[0])
# 全局特征重要性
shap.summary_plot(shap_values, X_test)
```

### 4.3 可解释性的法规要求

- **GDPR 第 22 条**：完全自动化决策的"获得解释权"
- **EU AI Act**：高风险 AI 系统必须提供"充分透明度"
- **中国个人信息保护法**：自动化决策需说明并允许拒绝

## 五、算法备案与合规框架

### 5.1 中国算法备案制度

根据《互联网信息服务算法推荐管理规定》与《生成式人工智能服务管理暂行办法》：

| 服务类型 | 备案要求 | 关键义务 |
|---------|---------|---------|
| 推荐算法 | 必须备案 | 提供关闭选项、用户标签管理 |
| 深度合成 | 必须备案 | 显著标识、内容溯源 |
| 生成式 AI | 必须备案 + 安全评估 | 训练数据合规、内容标识 |

### 5.2 备案流程（中国生成式 AI）

```
1. 准备材料（算法机制说明、训练数据来源、安全评估报告）
2. 网信办备案
3. 安全评估（自评估 + 第三方评估）
4. 通过后上线，持续报告
```

## 六、主要法规对比（EU AI Act、中国生成式 AI 管理办法、美国行政令）

### 6.1 三大法规对比

| 维度 | EU AI Act | 中国生成式 AI 管理办法 | 美国行政令 14110 |
|------|-----------|---------------------|-----------------|
| 性质 | 立法（强制） | 部门规章（强制） | 行政指导（非强制） |
| 时间 | 2024 通过，2026 全面生效 | 2023.8 生效 | 2023.10 签署 |
| 监管思路 | 基于风险分级 | 全流程管理 | 部门协同 + 自律 |
| 风险分级 | 4 级（不可接受/高/有限/最小） | 不分级但区分场景 | 不分级 |
| 重点 | 高风险 AI 严格合规 | 生成内容标识 + 数据合规 | 安全测试 + 标准制定 |
| 处罚 | 高达营业额 7% | 警告/罚款/下架 | 主要靠行业自律 |

### 6.2 EU AI Act 的风险分级

| 风险等级 | 例子 | 监管要求 |
|---------|------|---------|
| **不可接受** | 社会评分、操纵性 AI | 禁止 |
| **高风险** | 招聘、信贷、司法、医疗 | 严格合规、登记、人审 |
| **有限风险** | 聊天机器人、深度合成 | 透明义务（标识） |
| **最小风险** | 垃圾邮件过滤 | 无强制要求 |

### 6.3 中国生成式 AI 管理办法要点

- 训练数据：来源合法、尊重知识产权、个人隐私
- 输出内容：标识 AI 生成、防违法有害信息
- 服务提供者：承担网络信息内容生产者责任
- 用户：实名认证、内容责任

## 八、AI 伦理审计实践

### 8.1 审计的五大维度

| 维度 | 审计内容 | 方法 |
|------|---------|------|
| 数据 | 来源合规、标注质量、偏见 | 数据卡（Datasheet） |
| 模型 | 性能差异、鲁棒性、安全 | 红队测试、对抗评估 |
| 流程 | 文档完整、决策可追溯 | 流程审查 |
| 部署 | 监控有效、降级机制 | 演练测试 |
| 影响 | 用户与社会影响 | 影响评估（IA） |

### 8.2 模型卡（Model Card）示例

```markdown
# 模型卡：客服对话模型 v2.3

## 模型概述
- 用途：电商客服自动回复
- 架构：基于 Llama-3 微调
- 训练数据：500 万条历史客服对话（脱敏）

## 评估
- 整体准确率：87%
- 分群体准确率差异 < 2%
- 拒答率：3.2%（敏感问题）

## 局限
- 不支持多轮长对话
- 对小语种支持差
- 涉及价格/库存可能出错，必须 RAG

## 使用条件
- 必须接入订单系统
- 关键操作需人工审核
- 每月再评估
```

## 九、负责任 AI 实施指南

### 9.1 RAI 实施路线图

```
阶段 1（1-3 月）：建立治理架构
  - 设立 AI 治理委员会
  - 发布 AI 伦理准则
  - 现有 AI 资产盘点

阶段 2（3-6 月）：流程嵌入
  - 项目立项时强制伦理评估
  - 建立评估工具集（公平性、可解释性）
  - 关键岗位培训

阶段 3（6-12 月）：技术落地
  - 上线监控（漂移、公平性、安全）
  - 建立红队机制
  - 完善备案与文档

阶段 4（持续）：文化沉淀
  - 把 RAI 嵌入 OKR
  - 外部审计与披露
  - 行业标准参与
```

- [ ] 是否提供可解释性？
- [ ] 是否有人工兜底与申诉机制？

### 9.3 常见误区

| 误区 | 真相 |
|------|------|
| 伦理 = 合规 | 合规是底线，伦理要求更高 |
| 等做大了再治理 | 越晚治理成本越高，可能违法 |
| 技术能解决一切 | 80% 是流程与文化问题 |
| 公平 = 准确率一致 | 公平有多个互斥定义 |
| 透明 = 开源 | 透明是决策可理解，不一定开源 |
